# Developer onboarding

This is the shortest supported path from a repository to a reviewed Noru change. The pull-request
path is deliberately read-only; publishing is a separate, protected action.

## 1. Install the hub and only the pieces you need

Install `noru` first, then ask it to review the branch. You do not need to choose every piece up
front. Client-specific install and MCP setup are documented for
[Codex](./clients/codex.md), [Claude Code](./clients/claude-code.md),
[Cursor](./clients/cursor.md), and [other MCP clients](./clients/generic-mcp.md).

```text
/noru:connect
/noru:doctor
/noru:review
```

`connect` must show the organization you intend to update. `doctor` checks the local toolchain,
cache hygiene, and possible competing privacy data-map publishers. `review` compares the current
branch with `origin/main`, discovers the installed pieces, runs and validates the relevant local
scans, and writes nothing to Noru. It can create local `.noru/*.yml` review artifacts. Use
`--base-ref=<ref>` if the repository has a different default branch. `/noru:status` is the separate
read-only view of live work requiring attention in Noru.

## 2. Create the reviewable artifact

Review the files generated by `/noru:review`. If a piece needed additional input or was selected
explicitly after the branch review, run its scan directly:

```text
/<piece>:scan
```

Commit `.noru/<piece>.yml`; never commit `.noru/.cache/`. For `privacy-datamap`, also review and
commit `.noru/privacy-datamap.lock.json` and `.fides/datamap.yml`: the lock pins the machine-observed
structure accepted with the review, the Fides file is the ecosystem export, and
`.noru/privacy-datamap.yml` carries the owners, citations, and decisions used by the gate. Resolve
every `needs_review` item with a named owner and rationale rather than accepting classifier output
as a compliance conclusion.

## 3. Add a credential-free pull-request check

Copy [`templates/github/noru-grc-review.yml`](../templates/github/noru-grc-review.yml) into the
adopting repository as `.github/workflows/noru-grc-review.yml`. It starts in warning mode, pins a
release tag, detects the relevant pieces from the branch, and produces one consolidated report. The
full checkout is required when comparing findings with the merge base.

```yaml
name: grc
on: [pull_request]

permissions:
  contents: read

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v7
        with:
          node-version: "20"
      - uses: noru-tech/noru-review-action@v0
        with:
          base-ref: ${{ github.event.pull_request.base.sha }}
          mode: warn
          gate-on-new: true
```

This path runs local collection, validation, expiry, and policy checks. It needs no Noru secret and
has no input capable of running diff or push. Change `mode` to `gate` after the report is understood
and the committed manifests are current. Pass `pieces: privacy-datamap,ai-inventory` only when the
repository wants an explicit adopted set instead of automatic branch routing. A fork receives no
credential; checks needing an external queue say `skipped`, never `passed`.

## 4. Review the exact Noru change

In an authenticated MCP client, run:

```text
/<piece>:diff
```

The plan is short-lived and bound to the manifest bytes, repository commit, plugin version, MCP
endpoint, required scopes, and exact Noru organization. A changed branch, manifest, connection, or
expired plan requires a new diff. Read the create/update/close counts and the target organization
before approving it.

## 5. Publish through one protected path

After approval, run `/<piece>:push`. In an authenticated MCP host the agent executes the reviewed
calls. In CI, `steps: all` with `NORU_API_KEY` in the job environment builds the snapshot, writes
the plan, and executes exactly the calls `:push` emitted, reporting them written only with a receipt
that says every call succeeded ([CI mode](./ci-mode.md#the-publication-half-and-why-it-is-separate)).
`ai-inventory` and `privacy-datamap` need a person to build their snapshot, so in CI they publish
only from a snapshot passed with `state:`. Do not replace any of this with a direct REST call that
bypasses the reviewed plan.

Put automated publication on a protected branch or deployment environment with human
approval—never `pull_request_target`—and make that workflow the only writer for the source. Keep PR checks read-only. `/noru:doctor` warns when tracked code or
workflows indicate more than one privacy data-map publisher or repeat its source slug, but the
warning is a signal to review, not proof that both paths are active.

See [CI mode](./ci-mode.md) for exit codes, GitLab and shell examples, policy baselines, and staged
adoption.
